Standard Operating Procedure & Runbook

Monthly Windows Server Patching — Azure Update Manager (Arc-Enabled, VMware vCenter-Hosted Fleet)

Document Type: SOP + Runbook Classification: Internal / Operations Version 1.0

1. Document Information

1.1 Purpose

This document defines the standard, repeatable procedure for performing monthly Windows Server patching across a VMware vCenter-hosted, Azure Arc-enabled server fleet, using Azure Update Manager (AUM) as the patch orchestration platform. It combines governing policy (SOP) with step-by-step execution instructions (Runbook) to ensure patching is performed consistently, safely, and with full auditability.

1.2 Scope

This SOP applies to all Windows Server virtual machines that are hosted on VMware vCenter and registered as Azure Arc-enabled servers, and that fall within a monthly patching cycle managed through Azure Update Manager. It covers the full lifecycle from Change Request approval through evidence collection and change closure. It does not cover non-Windows operating systems, non-Arc-enabled infrastructure, or ad hoc emergency/out-of-band patching, which are governed by separate procedures.

1.3 Objectives

#Objective
1Ensure all in-scope Windows Server VMs receive applicable security and quality updates within the approved monthly maintenance window.
2Minimize business disruption through structured scheduling, snapshotting, and backup coordination.
3Provide a consistent, auditable evidence trail for every patching cycle.
4Standardize rollback and exception handling to reduce recovery time on failure.
5Enable operational scaling through Azure Arc tag-based targeting rather than manual VM selection.

1.4 Audience

Windows Team, Azure Administrators, VMware Administrators, Backup Team, Change Manager, CAB members, Operations Manager, Application/Service/VM Owners, and internal or external auditors reviewing patch compliance evidence.

1.5 Assumptions

Assumptions
  • All target VMs are already onboarded to Azure Arc and reporting a Connected status prior to the start of a patching cycle.
  • All target VMs have outbound internet connectivity to Microsoft Update endpoints.
  • VMware vCenter is reachable and functional for snapshot operations during the maintenance window.
  • A Change Management process (CR/CAB) is operational and mandatory prior to implementation.
  • Four implementation engineers are available and workload is distributed across them for each cycle.
  • Backup schedules can be adjusted by the Backup Team on request ahead of the maintenance window.

4. Pre-Implementation Activities

Executed by the assigned implementation engineer(s) in the hours prior to the maintenance window, typically T-24h through T-1h.

4.1 Review Approved CR

  • Confirm CR number, scope (VM list/tag), window, and assigned engineers
  • Confirm rollback plan is attached to the CR

4.2 Confirm Maintenance Window

  • Cross-check CR window against AUM Maintenance Configuration schedule
  • Confirm no overlapping change activity on the same VMs

4.3 Notify Stakeholders

  • Send Start Notification template (Section 10.1) to VM Owners, Service Owners, and Application Owners at T-24h

4.4 Confirm Backup Schedule Modification

  • Request Backup Team pause/adjust standard backup jobs for target VMs during the window
  • Obtain written confirmation from Backup Team

4.5 Verify Latest Successful Backup

  • Confirm each target VM has a successful backup within the last 24 hours
  • Escalate any VM without a recent successful backup — do not patch until resolved or formally accepted as risk by the Change Manager

4.6 Verify Azure Arc Connectivity

  • Confirm all target VMs report Connected in Azure Arc
  • Investigate and remediate any VM in Disconnected or Error state before proceeding

4.7 Verify Azure Update Manager Readiness

  • Confirm Maintenance Configuration scope resolves the expected VM count
  • Confirm patch schedule settings (reboot behavior, patch classifications) are correct

4.8 Verify VM Power State

  • Confirm all target VMs are powered on and responsive

4.9 Verify Monitoring Status

  • Place target VMs in scheduled maintenance mode in monitoring tools to suppress false alerts

4.10 Verify Azure & VMware Permissions

  • Confirm implementation engineers have required Azure RBAC roles (e.g., Update Manager operations)
  • Confirm implementation engineers have required vCenter roles for snapshot operations
Validation Checkpoint — Pre-ImplementationAll ten items in Sections 4.1–4.10 must be confirmed complete and logged in the CR before moving to Section 5.

5. VMware Snapshot Procedure

Snapshots provide the primary rollback mechanism for this SOP and must be created for every target VM before any update is downloaded or installed.

5.1 Snapshot Naming Convention

PreUpdate_<YYYYMMDD>_<CRNumber>

Example: PreUpdate_20260805_CR102345

5.2 Description Format

Pre-patch snapshot | CR: <CRNumber> | Engineer: <Name> | Window: <Date/Time> | Purpose: Monthly Windows Patching Rollback Point

5.3 Snapshot Execution Steps

  1. Confirm no existing snapshot chain exceeds organizational retention/performance limits before creating a new one.
  2. Create snapshot with memory state excluded (memory snapshot not required for patch rollback use case) unless application-specific requirements dictate otherwise.
  3. Apply naming convention (5.1) and description format (5.2).
  4. Monitor snapshot task in vCenter Recent Tasks until status = Completed.

5.4 Snapshot Verification

  • Confirm snapshot appears in the VM's Snapshot Manager
  • Confirm snapshot task status = Success
  • Confirm timestamp matches the current patching cycle

5.5 Handling Failures

On Snapshot Failure Do not proceed with patching for the affected VM. Retry once. If failure persists, escalate to VMware Admin and Change Manager; remove the VM from the current cycle's target scope and document the exclusion in the CR under Section 12 (Exception Handling).

5.6 Documentation Requirements

  • Log snapshot name, timestamp, and task ID against each VM in the evidence tracker
  • Attach a screenshot of the Snapshot Manager for each VM (or a consolidated view for tag-grouped batches)

6. Azure Arc Tagging Procedure

Azure Arc tags are applied before each cycle to group in-scope VMs so that Azure Update Manager operations (assessment, scheduling, deployment) can target the entire patch group by tag query instead of manually selecting individual servers. This reduces selection errors, supports dynamic-scope Maintenance Configurations, and keeps the CR-approved scope directly traceable to what AUM actually executes against.

6.1 Tag Naming Convention

PatchGroup = <SiteCode>-<YYYYMM>

6.2 Recommended Tag Structure

6.3 Example Tags

6.4 Validation

  • Query the Maintenance Configuration's dynamic scope and confirm the resolved VM count matches the CR-approved list
  • Spot-check a sample of tagged VMs individually to confirm tag values are correct

6.5 Removing Tags After Completion

Note Cycle-specific tags (e.g., PatchGroup with a month value) should be removed or superseded after the cycle closes to prevent accidental inclusion in future dynamic-scope queries. Persistent tags (e.g., Site) remain.

7. Patch Deployment Procedure

Phase 1 — Assessment
  1. Trigger an on-demand Assessment in Azure Update Manager against the tagged scope (do not rely solely on the periodic auto-assessment).
  2. Review the missing updates list per VM, noting update classification (Critical, Security, Definition, etc.).
  3. Validate assessment results against expected baseline (e.g., known pending KBs from prior cycle).
CheckpointDo not proceed to Phase 2 until assessment has completed for 100% of the tagged scope.
Phase 2 — Download
  1. Initiate update download via the scheduled Maintenance Configuration run or manual "Install now" (download step is implicit within AUM's install operation).
  2. Monitor download/prep progress per VM in the Update Manager operations blade.
  3. For failures, capture the error code and consult Section 12 (Exception Handling) before retrying.
Phase 3 — Installation
  1. Confirm installation is scoped only to approved patch classifications defined in the CR.
  2. Monitor per-VM installation status (In Progress / Succeeded / Failed / Completed with warnings).
  3. Record installation status per VM in the evidence tracker as it completes.
Phase 4 — Reboot
  1. Allow AUM to perform the mandatory reboot where required by installed updates (per environment rule: reboot is mandatory whenever required).
  2. Validate server availability post-reboot (ping, RDP/WinRM reachability, service state).
  3. Validate Azure Arc reconnects and returns to Connected status within an acceptable time (typically under 15 minutes).
Watch ForVMs that reboot but do not reconnect to Arc within the expected window — treat as an exception per Section 12.
Phase 5 — Post-Reboot Assessment
  1. Run a fresh Assessment against the same tagged scope after reboot completes.
  2. Confirm zero pending applicable updates for the approved classifications.
  3. Identify and document any VM with remaining pending updates as an exception, with root cause where known (e.g., update requiring a second reboot cycle).

11. Rollback Procedure

11.1 Patch Installation Failure

  1. Stop further update actions on the affected VM.
  2. Review installation error/log for root cause.
  3. If not resolvable within the window, proceed to snapshot restoration (11.4).

11.2 Server Inaccessible

  1. Attempt console access via vCenter to confirm VM state.
  2. If VM is unresponsive or in a boot-loop, proceed to snapshot restoration (11.4).

11.3 Application Failure

  1. Engage Application Owner to confirm impact and whether rollback is required.
  2. If rollback is confirmed necessary, proceed to snapshot restoration (11.4).

11.4 Snapshot Restoration

  1. Power off the VM if still running.
  2. Revert to the pre-patch snapshot identified in Section 5.
  3. Power on the VM and confirm boot to a healthy state.

11.5 Validation After Rollback

  • Confirm VM is reachable and services are running
  • Confirm Azure Arc reconnects
  • Confirm application functionality with Application Owner
  • Remove the VM from the current cycle's completed scope and log as rolled back

11.6 Stakeholder Communication

  • Send Failure Notification (Section 10.5) immediately upon rollback decision
  • Update the CR with rollback details, timestamp, and cause

12. Exception Handling

ExceptionImmediate Action
Assessment failureRetry once; if it persists, check Arc agent health and exclude VM from cycle if unresolved
Azure Arc offlineAttempt agent restart via console; escalate to Azure Admin; exclude VM from cycle
VM unreachableCheck vCenter power/console state; engage VMware Admin
Update installation failureCapture error code; retry once; if it persists, initiate rollback (Section 11)
Reboot failureAttempt console-based reboot; if VM does not return, initiate rollback
Snapshot failureExclude VM from cycle per Section 5.5; do not patch without a rollback point
Backup unavailableEscalate to Change Manager for risk acceptance decision before proceeding
Internet connectivity issuesVerify proxy/firewall path to Microsoft Update; escalate to network team if unresolved

Every exception is logged against the CR with timestamp, VM name, description, and resolution/escalation path, regardless of whether it was ultimately resolved within the window.

13. Post-Implementation Activities

  • Remove cycle-specific tags (Section 6.5), if applicable
  • Verify monitoring agents removed from maintenance mode and reporting normally
  • Verify Backup Team has resumed standard backup schedules
  • Update the Change Request with final implementation notes and outcomes
  • Attach all evidence collected in Section 9
  • Close the implementation record / move CR to Review or Closed status per ITSM workflow
  • Document lessons learned for the cycle (recurring failures, timing issues, scope gaps)

16. Best Practices

AreaBest Practice
Maintenance windowsKeep windows consistent month-to-month to build predictable stakeholder expectations and simplify backup coordination.
Tagging strategyUse cycle-scoped tags (with date/CR embedded) rather than permanent static groups, to prevent scope drift between cycles.
Snapshot managementAvoid retaining pre-patch snapshots longer than necessary; long-lived snapshots degrade VM performance and consume datastore capacity.
Backup coordinationConfirm backup adjustment in writing before every cycle — never assume the prior month's arrangement still applies.
Validation methodologyValidate against a defined baseline (previous month's healthy state) rather than judgment alone.
DocumentationLog evidence as each phase completes rather than reconstructing it after the window closes.
Audit readinessEvery screenshot must independently show VM name, date, and time — assume no other context will be available to the reviewer.
Security considerationsRestrict snapshot and AUM operation permissions to the implementation engineer role; review access quarterly.
Performance considerationsStagger reboots across the four-engineer workload to avoid simultaneous domain controller or shared-service impact.
Risk mitigationNever skip the snapshot step to save time, even under schedule pressure — it is the sole rollback mechanism defined in this SOP.
